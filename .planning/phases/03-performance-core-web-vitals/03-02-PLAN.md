<threat_model>
This plan edits two source files inside the AdSense consent gate and runs a CWV audit. It does not touch network, storage, auth, or user-input surfaces. ASVS L1 review:

- **AdSense consent gate bypass:** the highest-priority risk. If the minHeight reservation accidentally bypasses the `if (!consent) return null` early-return, the `<div className="adslot">` (and possibly the `<ins>`) would render for non-consenting users, which is both a regulatory issue (GDPR / consent leakage) and an AdSense policy issue. Mitigation: T2's action requires the inline style be added to the existing return JSX, leaving the two early-return statements at lines 55–56 byte-for-byte intact; T2's acceptance criteria include a grep confirming both `return null` lines remain present and the order `consent gate → route gate → return JSX` is unchanged.
- **`cookie-consent-changed` event API drift:** any change to the listener attach/detach in `AdSlot.jsx` could break `useAdSenseLoader`'s coordination. Mitigation: the `useEffect` adding/removing the `cookie-consent-changed` listener is byte-for-byte unchanged; only the JSX return block gains an inline `style` attribute. Acceptance criteria require `grep -c "cookie-consent-changed" src/components/AdSlot/AdSlot.jsx` to remain at 1 and the event name to be the literal string (no rename to `cookieConsentChanged` or similar).
- **`STORAGE_KEY` constant exposure:** the storage key (`'cookie-consent'`) lives in `CookieConsent.jsx` and is not imported by AdSlot. This plan does not touch `CookieConsent.jsx`. Mitigation: `files_modified` does not include `CookieConsent.jsx`; final pass includes a grep diff confirming zero edits to that file.
- **Unauthenticated ad-slot id exposure:** `SLOT_RESERVATIONS` is keyed by the existing `homeEditorial` / `guideMid` / etc. identifiers, NOT by the numeric slot ids in `AD_SLOTS` (`0000000001`, etc.). The numeric ids are already public (they ship in the rendered HTML as `data-ad-slot`); adding a reservation map keyed by the human-readable name does not introduce any new disclosure. Mitigation: T1 acceptance criteria require the map keys be the exact strings `homeEditorial`, `guideMid`, `guideEnd`, `pairBelowConversion`, `pairEnd` — not the underlying numeric ids.
- **CLS regression on bad reservation values:** if `SLOT_RESERVATIONS` heights are too small, the actual ad will still produce CLS when it expands beyond the reserved box; if too large, a permanent empty area shows on the page. Mitigation: D-05 values are aligned with standard AdSense responsive sizes (250 = medium rectangle, 280 = large rectangle / responsive auto); T4 measures CLS on three pages and T5 remediates if any page exceeds the 0.1 threshold.
- **AdSense reviewer regression risk:** this is the most reviewer-visible plan in the sprint. Mitigation: every edit keeps `npm run build` green; T3 spot-checks the wrapper renders the expected min-height in DevTools before the Lighthouse pass starts; T7 explicitly verifies Phase 1 + 2 invariants on the deployed prod surface.
- **No new outbound network calls:** Lighthouse runs are pulled by the Chrome DevTools panel and never invoked from the codebase. The site itself adds zero new third-party hosts.

Severity ceiling: none at `high`. Proceed.
</threat_model>
